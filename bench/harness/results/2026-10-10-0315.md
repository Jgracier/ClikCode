## Analysis (written by hand after the run)

Builds: 2026-10-10 is the first run (sandbox off by default then); 0308 is
ClikCode alone on the sandbox-on build; 0315 is both on the build with the
fixes below. The sandbox (bwrap, on by default) refused nothing in any task.

Fixed in ClikCode after the first two runs:

- Every Gateway turn waited for ClikDeploy's MCP server before its first
  model step, up to the 30 s connect timeout: task 01 took 45 s in 0308
  (tools/list timed out), and two first-run tasks stalled 4.8 s and 9.7 s.
  Now a 3 s turn wait (setup before the first step: 0.36-0.6 s in 0315).
- `send --model claude-sonnet-5-5` was refused before any turn because the
  Gateway's /v1/models omitted it for a moment (its lists flap between 203
  and 155 models); now looked up again on a fresh list.
- wait could not wake on a background server being ready, so the model ran
  `sleep 4` + bash_output (01 run) or polled a log (0308). wait now takes an
  output regex; in 0315 the model used it (`Wait for bash_1 to print
  /listening on/`). bash's description also says no trailing `&` with
  run_in_background (0308 lost the server's output that way).

Still slower, and why (open):

- Edits: 03 and 06 are 2x Claude Code. ClikCode's model edits file by file
  with edit_file/multi_edit (2.6k and 3.8k output tokens vs 1.3k and 2.3k)
  because the bash tool forbids editing with shell commands; Claude Code's
  model rewrote all files in one sed/python Bash call. Output tokens are the
  cost at ~95 tok/s.
- Per step, the Gateway route adds ~0.4 s over Claude Code's direct API
  (01: 1.4-1.6 s vs 0.9-1.1 s for the same small steps).
- A headless `clikcode send` leaves its session worker idle for 30 min after
  exiting (the "leftover procs" column).
- 0308 tasks 02 and 03 read nothing from the prompt cache (cost $0.25 and
  $0.19 instead of ~$0.09): the Gateway's caching, not the request prefix.
- The Gateway reports no cost to ClikCode (costUsd 0), so ClikCode's cost
  column is an estimate.
